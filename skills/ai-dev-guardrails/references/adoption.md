# 给现有项目接入第一条规则

假设一个团队用命令行工具导出账本，另一个团队的脚本每天读取它的 JSON 输出。某次重构把字符串编号 `"007"` 写成数字 `7`。导出仍然成功，按编号关联的旧记录却找不到了。

先看旧版本输出、消费脚本和项目对格式的约定。若调用方确实依赖编号原值，把下面这一行放进已有的契约说明，再从仓库的 AI 开发入口链接过去。小项目用一行表格即可。

| 规则 | 适用范围 | 级别与原因 | 执行位置 |
| --- | --- | --- | --- |
| export.record-id | 账本的 JSON 输出 | MUST。编号是字符串，前导零参与匹配；允许增加可选字段 | 通过 CLI 输入两条编号，按旧调用方的读取方式取回并比较 |

随技能提供的例子可以在本地运行。从技能目录执行：

```sh
python3 -B -m unittest discover -s examples/cli-contract -p 'test_*.py' -v
```

在临时副本里把 `report.py` 的输出字段从 `id` 改为 `record_id`，原用例会因旧字段缺失而失败。恢复 `id`，再增加一个可选字段，测试应通过。只断言消费者依赖的字段，便能同时保住兼容性和扩展空间。

## 在自己的项目里换成什么

| 项目里真正会出错的事 | 检查该放在哪里 | 怎样证明拦得住 |
| --- | --- | --- |
| 预约页面接受了同一时段的第二次预约 | 负责写入预约的业务入口 | 用两份独立请求预约同一资源，只允许一次成功，重新读取后也只有一条记录。若承诺覆盖并发，验证实际存储并发语义。 |
| 列表只显示本人记录，导出却多了别人的行 | 导出入口及它实际调用的数据层 | 用两个归属不同的合成记录，验证有导出权限的人只收到范围内的一行。单独检查没有导出权限时的拒绝结果。 |
| 批处理失败后重跑，同一事件被重复计入 | 任务的持久化边界 | 从已处理部分记录的状态恢复，用同一批输入重试，核对最终数据和事件数。 |
| 库的内部重构改变了下游用法 | 最小下游程序或现存消费项目 | 按受支持的旧签名运行同一调用，比较调用方依赖的返回值或异常。 |

## 仓库里保留什么

- 在已有的贡献指南、`AGENTS.md` 或团队等效入口注明业务归属、权威规则位置和验证命令。多个工具用同一份正文。重大取舍写进现有的架构决策记录。
- 已有 CI 时，把针对该契约的测试加入本地也能执行的任务。CI 尚未建立时，先交付能运行的命令，说明当前由谁、在什么环节运行。
- 有多个工具读取同一条规则时，用稳定的规则 ID 指向同一份定义。MUST 失败时先修复；若需求确实更改，审阅契约及受影响的调用方。只有明确允许偏离的规则可按约定期限豁免。
- 项目使用代码生成时，注明哪些文件由生成器维护，以及业务代码如何审阅模板升级。环境之间移交配置时，按稳定的业务键比较上次基线、待导入内容与目标现状，识别会覆盖目标独立修改的项。
- 交接写能核对的事实。例如「旧客户端测试通过；测试环境尚未跑每日消费任务；下一步用测试账本跑一次导出与关联」。让接手者能够直接复验。
